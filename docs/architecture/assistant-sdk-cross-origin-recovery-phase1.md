## Existing SDK findings (not silently worked around)

Actual: neither root nor nested state is frozen; `node --input-type=module` importing `createAssistant`, then `const a=createAssistant({bindEvents:false}); const s=a.getState(); s.network.online='tampered'; console.log(a.getState().network.online)` prints `tampered`, without an emit. 2. **React adapter reuses a destroyed instance:** `src/adapters/react.js`, `createReactAdapter`'s `resolveAssistant` permanently caches `cachedAdapterAssistant`; `getExternalStoreBindings` attempts re-resolution after destruction but that getter returns the same destroyed instance. 3. **Release-guide contradiction:** `packages/assistant-sdk/README.md:8-10` says 0.4.0 is unpublished, while line 454 instructs `npm install @youge/assistant-sdk@0.4.0` without conditioning it on publication. ## Proposed public API (not existing API)

Extend the Assistant instance rather than exporting controller factories. An explicitly trusted host calls e.g. `assistant.configureRecovery({ projectId, activeEnvironmentId, environments, hooks })`; results distinguish configured, identical/idempotent and conflicting. Each finite entry contains environment ID, project ID, configuration revision and two distinct exact canonical HTTPS origins. Require one selected environment and exact current `location.origin` membership; reject credentials, path other than `/`, query, fragment, opaque origins, duplicate/ambiguous pairs, malformed origins and unrelated registry changes. Revision changes use explicit invalidation/reconfiguration, not silent `attach` merging. Recovery configuration and hooks come only from trusted deployment bootstrap; do not load from URL, local preferences or generic published/LKG config. `configureRecovery` is proposed as part of the existing instance, not another global config authority.

Expose one `assistant.recovery` facade (or equivalent typed instance methods): `getState`, `subscribe` via existing assistant store, `checkHealth`, `requestFallback`, `requestReturnToPrimary`, `retryEvaluation`, `invalidatePolicy`, `invalidateSession`, `invalidateConfiguration`, `cancel`, `stop`. Readonly stable recovery state contains project/environment/role, health, phase, redacted reason and typed error code, policy mode/availability/revision/receipt/expiry, non-sensitive session status, attempts/cooldown and permitted actions. Typed lifecycle events include state changed, evaluation started/completed, manual action required, transition scheduled/failed/cancelled, primary restored, return required, and destination session unavailable. Events and state never contain hook payloads, exceptions, tokens or arbitrary URLs. Define explicit result types for rejected, cancelled, unavailable, busy and scheduled; scheduled is not arrival.

Use existing React store snapshot and action dispatch, with a stable disabled SSR snapshot, no side effects in render and no component-created controller. On configured instances, recovery actions call the controller and **do not emit the legacy actionable event**; if a compatibility notification is needed, use a distinct explicitly observational event, since legacy listeners may ignore ownership marks. Without configuration preserve legacy dispatch exactly. Direct calls enforce identical capability and safety gates. Classic widget and generated bundle need explicit integration or documented incompatibility; do not assume changing React alone solves duplicate ownership. Evaluate the repository's no-`fetch`/no-`setInterval` core rule: use injected host probe/policy adapters and bounded cancellable one-shot scheduling; do not add hidden network requests or timers to generic diagnostics. A host readiness adapter is constrained to a given role/origin and cannot choose a destination.

## Policy delivery and authorization

One project-wide logical mode/revision is administered and distributed by the host, independently authenticated for each environment. Proposed hook obtains an environment-scoped authenticated policy assertion from an explicitly configured independent authority, reachable without the failing primary, or supplies a previously verified signed assertion. Verification is performed by a trusted environment-specific verifier with pinned keys/issuer/audience; the SDK validates the returned verified claims against exact project, environment, authority, config revision, mode, revision, issued-at and expiry. A plain boolean, unverified object, localStorage value, browser-provided receipt time, cross-environment assertion or arbitrary hostname is not evidence. A compromised host bootstrap, verifier, or same-origin script is outside an in-browser SDK's trust boundary; document CSP/XSS and deployment trust.

Proposed strict maximum is **30 seconds from signed issuance**, additionally limited by signed expiry, verified receipt age, authorization expiry and a monotonic elapsed clock for in-process deadlines. Check wall-clock plausibility, future issuance and clock discontinuities; fail closed on uncertainty. Re-reading/re-verifying a cache must not reset issuance age or extend expiry. Store no credentials. A trusted per-environment revision high-water mark must be obtained from a fresh authenticated authority or tamper-resistant host mechanism; in-memory high-water prevents rollback only in the current lifetime. After cold start, signed cache alone cannot prove it is the latest revision; absent a trusted checkpoint, automatic switching is blocked, not guessed. A revocation push invalidates in-flight work immediately; otherwise an old assertion can authorize until its <=30-second window ends, assuming clocks are reliable. An unreachable authority allows only a still-valid verified assertion meeting these constraints; otherwise expose `policy-unavailable` and block automatic transition. Manual actions still require valid policy, authorization and safety gates for this proposed design; confirm this availability trade-off with the owner. Signing keys, key rotation, revision checkpoints, clock skew, outage availability and policy-to-auth binding need host review.

## State machine and execution

- Invalid/absent opt-in → `disabled`; primary starts unknown until checked. Positive primary → `primary-healthy`; one failure → `primary-degraded`. Only two consecutive separately timed confirmed transport-unreachable/timeouts (not cancellation/offline/opaque/redirect/HTTP status) → `evaluating`. Primary recovery resets the counter. DNS/TLS/CORS filtering cannot be identified with certainty.
- `evaluating` validates policy, readiness and eligibility. Manual policy → `manual-required`; automatic may proceed only after all gates. Manual request also performs fresh evaluation, never bypasses gates. Positive readiness means readable, bounded, anonymous response with redirect rejection; unknown/unavailable blocks. Offline, 401/403, ordinary 4xx/5xx, one timeout, opaque and redirects do not independently trigger automatic fallback. `recovery-failed` exposes bounded retry/cooldown and explicit reasons, not blind loops.
- The transition is serialized: revalidate exact active role and config → policy → visibility/online and retry budget → destination readiness → unsaved-work consent → environment-scoped host authorization → host session preparation outcome → final checks → `switching-to-fallback` / `switching-to-primary` and one exact-origin-root navigation. Recheck epoch, deadlines, visibility and all appropriate freshness after **every** await and immediately before the synchronous executor. Any stale result is discarded; AbortSignal is advisory, not a substitute for epoch checks. Cancel on configuration/policy/session changes, expiry, sign-out, document ineligibility, stop or destroy. No path/query/hash or private data is passed to navigation.
- Destination initializes independently: it determines its actual role from exact document origin, calls host-owned redemption/verification and reports `fallback-active` only based on actual destination startup; it must not infer arrival or session from scheduled navigation. If host session verification fails, `destination-auth-required`; preserve the usable source session. Destination health does not imply authentication. Host protocol must prove account continuity, one-time redemption, environment-specific audience, revocation and expiry without credentials in URLs/SDK state.
- On fallback, bounded low-frequency user-initiated or scheduled probes require sustained positive primary readiness before `primary-restored` then `return-required`. Return always requires user confirmation, even under automatic policy, and repeats policy, unsaved-work, auth, session and final gates. Never auto-return. If primary auth is unavailable, show `destination-auth-required` and allow safe later retry.
- Own one controller per instance plus an exclusive document-scoped ownership lease shared among instances; conflicting instances fail explicitly. Single executor and navigation lock prevent duplicate calls in the document. Other tabs and cross-origin documents do not share JS state, Web Locks or storage; a browser-only lock cannot guarantee global exclusivity. Use bounded local retries/cooldowns, no automatic return and host-enforced environment-scoped transition/replay control for cross-document loop prevention. If a required exclusive lease or trustworthy host coordination is unavailable, fail closed; never present browser local storage as an authoritative lock. Exact coordination semantics need protocol review.

## Threat model / compatibility

Defend against malicious/incorrect aliases, mixed Production/Preview policy or grants, policy replay/rollback, stale asynchronous callbacks, redirects, session confusion, secret leaks, competing handlers, repeated clicks, tab duplication and disappearing readiness. Host hooks are trusted code but outputs are bounded, scope-checked and redacted; server authorities independently enforce authorization and destination sessions. No cross-origin credential CORS or assumed cookie/storage/worker sharing. Network observations do not prove filtering. SDK cannot help cold-start if the blocked primary prevents loading the SDK; host needs independent entry infrastructure. Destination/server behaviors cannot be guaranteed solely by SDK JavaScript.

Existing unconfigured consumers retain actions/events/config/exports and PWA/service-worker ownership. Configured recovery intentionally changes action ownership, requiring host-side legacy listener removal/delegation. Adding snapshot fields and dispatch result unions needs declaration and consumer compatibility tests. Classic runtime synchronization and precache integrity may require a kit version bump; repository rules require separate owner authorization rather than bypassing gates. A pre-1.0 **minor such as 0.5.0** is only a tentative option if additive and compatibility is demonstrated; otherwise assess breaking pre-1.0 release. No version recommendation is final before tests.
