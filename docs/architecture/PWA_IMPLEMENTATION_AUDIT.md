# PWA implementation audit

Audited against the repository at `302c338` and the focused fallback correction in this branch. Classifications describe the current implementation, not a promise that browser heuristics prove installation or worker ownership.

| Capability | Classification | Evidence and boundaries |
| --- | --- | --- |
| Install prompt and guidance | Complete for the existing flows | `src/runtime/pwa.js` captures `beforeinstallprompt`, consumes it once, observes `appinstalled`, and offers iOS/generic instructions or configured desktop QR. `tests/install-experience.test.mjs` exercises these flows. SDK `installation` delegates; it does not capture a second prompt. |
| Installed and display mode detection | Partially implemented | `isStandalone()` checks four display modes, iOS `navigator.standalone`, and Android referrer; `getState()` also uses the launch query, accepted prompt and `appinstalled`. Browser tabs cannot generally determine whether a separate installation exists. An accepted prompt is treated as installed for compatibility, not independent proof of a completed installation. Only the standalone media query is observed for changes. |
| Worker registration and ownership | Implemented but potentially unsafe for an existing host worker | The classic toolkit automatically registers its configured `data-sw`/scope on load when enabled and secure; registration can replace the script for an existing same-scope registration. Do not load it into a host-owned scope without planning the integration. The SDK core and bridge do not register, unregister, or take over a worker. This audit does not change the classic toolkit's existing lifecycle. |
| Update detection and waiting worker | Partially implemented | The toolkit detects an already-waiting worker and observes `updatefound` after registration, exposes `hasUpdate`, watches lifecycle and reconciles on visibility checks. An installation already in progress when registration resolves may have fired `updatefound` before the listener was attached. Detection also depends on browser service-worker behavior and a controlling worker. |
| Notification and controlled refresh | Partially implemented | Toolkit state and update events feed the SDK notification/action; `applyUpdate()` sends `SKIP_WAITING` to the waiting worker and reloads on `controllerchange`. Duplicate in-flight calls are guarded. The fallback now reloads only if that worker controls the page; otherwise it allows a retry. The toolkit's opt-in auto-update assumes a worker understands `SKIP_WAITING`; it cannot force a host worker to support it. Visibility reconciliation notifies state subscribers but does not dispatch an update event for a newly discovered waiting worker. |
| Status and diagnostics | Complete for the existing diagnostic scope | Toolkit `getState()`/`onChange()`, SDK `getState()` and existing on-demand network/DNS diagnostics provide status. Diagnostics are connectivity checks, not comprehensive service-worker health or installation verification. |
| SDK and integrations | Complete for existing contracts, subject to runtime limitations above | SDK installation and update methods delegate to the existing toolkit; `bridgePwaGlobals`, browser bundle, widget and React adapters reuse assistant state. Tests include `tests/sdk-integration.test.mjs` and `packages/assistant-sdk/tests/`. Unsupported or absent toolkit is handled with unavailable/unsupported results. |

## Compatibility and verification

No public APIs, identifiers, versions, storage keys or default registration settings changed. A successful `applyUpdate()` means the request was sent, not that activation is guaranteed. If no control change occurs after three seconds, the page stays in place and the waiting update remains retryable; a later unsolicited `controllerchange` does not force a reload. No worker registration or takeover was added. Existing host service-worker integrations must provide a compatible adapter rather than assume the classic toolkit is passive.

The regression harness verifies both the no-activation case and the missed-event case where the expected worker is already the controller. Real browser behavior, including browser-specific installation signals and worker activation delays, remains outside this Node harness.
